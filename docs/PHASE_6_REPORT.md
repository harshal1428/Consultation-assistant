# Phase 6 — Simulated Consultation Workflow Report

**Project:** VoiceSurg 3D — voice-driven facial-simulation prototype
**Scope of this phase:** wrap the existing voice→parameter pipeline and 3D
simulation in a complete, honest *simulated consultation* workflow — session
lifecycle, transcript, a proposal state machine with clarification/editing,
confirm/reject, an event history with undo, save/load/compare scenarios, and a
truthful consultation-summary export.
**Status:** implemented, unit-tested, built, and verified end-to-end at runtime
(real backend parser + headless Chrome)
**Date:** 2026-10-14

---

## 1. Objective & Boundaries

Add a consultation layer **around** the existing engine without changing it.

**In scope**
- A typed, fully in-memory consultation session model (no storage).
- Session lifecycle: start, end, reset, and "new consultation" with an explicit
  confirmation when unsaved work exists.
- A transcript that preserves the **original** spoken/typed text and keeps the
  parser's interpretation **separate** from it.
- A proposal state machine with clarification, per-instruction editing and
  removal, and an explicit mixed-batch policy.
- Confirm / reject with a double-submit guard; undo; reset.
- A session event timeline, with consecutive manual edits to the same parameter
  coalesced so a slider drag does not spam the log.
- Scenarios: save the current state, rename, delete, load, and compare any two
  states (baseline / current / each scenario) side by side with a parameter
  difference table.
- A Markdown consultation-summary export built from real session data.

**Explicitly out of scope (preserved)**
- The Phase 4 geometry engine is **not** replaced; no new facial regions beyond
  the nose.
- The Phase 2 UI is extended, not redesigned; Phase 5's six-parameter registry
  remains authoritative.
- The Phase 3 parser/AI provider is unchanged.
- No cloud persistence, database, authentication, EMR, or server storage.
- No claim of a compliant clinical audit trail, clinical accuracy, or
  outcome prediction.
- Phase 7 is **not** started.

## 2. The Consultation Model

Implemented in `frontend/src/scene/session/types.ts` and `logic.ts` (re-exported
through `frontend/src/scene/session/index.ts`).

The **applied simulation state stays in the existing `Command[]` history**
(`scene/transformations/logic`); the session model only records the *narrative*
around it, so there is exactly one source of truth for the model:

```
session : ConsultationSession
  id, startedAt, endedAt, status: "active" | "ended"
  transcript : TranscriptEntry[]   // original text + outcome, never overwritten
  proposals  : Proposal[]          // parse results + lifecycle
  events     : SessionEvent[]      // append-only narrative log
  scenarios  : Scenario[]          // full canonical state snapshots

history : Command[]  →  modelState = applyAllCommands(history)   // untouched engine
```

Every id is generated by `makeId(prefix)` (a monotonic counter + timestamp), and
all mutations are **pure functions** returning a new session — no side effects
inside React state updaters.

---

## 3. Session Lifecycle

| Action | Behaviour |
|---|---|
| Start | `createSession()` — status `active`, one `session_started` event. |
| End (`endSession`) | status `ended`, `endedAt` set, one `session_ended` event; a still-unresolved proposal is `cancelled`; new instructions are refused and inputs disabled. |
| Reset simulation | Clears the applied `history` and cancels the pending proposal; **keeps** transcript, timeline and scenarios; logs a `reset` event. Confirmed first when changes exist. |
| New consultation | Full reset of the in-memory session (new id, empty transcript/history/scenarios). Confirmed first when unsaved work exists. |

Async safety: a `sessionIdRef` + a request-token `reqRef` invalidate any in-flight
parse when the session changes, so a late backend reply can never leak into a new
session (see §9).

## 4. Proposal State Machine & Mixed-Batch Policy

`ProposalStatus` is adapted to the **real** parser contract, so no unreachable
state exists:

```
processing → needs_clarification | ready | blocked | failed
needs_clarification | ready | blocked → confirmed | rejected | cancelled
```

- `deriveProposalStatus()` maps the parsed instructions to `ready` (≥1
  applicable), `needs_clarification` (any ambiguous), or `blocked` (nothing
  applicable).
- Terminal states (`confirmed`/`rejected`/`cancelled`) are set once and never
  re-derived (`refreshProposalStatus` skips them, as it skips `processing`/`failed`).

**Mixed-batch policy (deliberate).** A change set is applied **in full or not at
all**:
- **Confirm & simulate** is **disabled** unless *every* instruction is applicable.
- A separate, explicitly labelled **"Apply only valid (n)"** action appears when a
  subset is valid — the partial application is always a conscious user choice,
  never silent.
- The partial path records `appliedAll: false` and `appliedCommandCount`, so the
  report states exactly what was applied.

This preserves Phase 3's "only `ok` instructions are ever applied" rule while
giving the surgeon an explicit way forward on a partly-understood utterance.

## 5. Transcript

`TranscriptLog` renders each `TranscriptEntry` with:
- its **source** (`voice`/`typed`) and time,
- the **original text** in quotes (never replaced by edits),
- an **outcome** chip (Awaiting review / Confirmed / Rejected / Cancelled /
  Failed / Processing),
- the **interpretation** (parsed instructions) shown separately beneath it.

---

## 6. Clarification & Editing

Each `InstructionCard` can be edited in place. In addition to operation / value /
unit, edit mode now exposes the **region** and **parameter** as selects populated
from the Phase 5 registry (`REGION_OPTIONS`, `parametersForRegion`), so an
instruction whose region was not recognised can be resolved. Saving an edit that
supplies the missing piece promotes a `needs_clarification`/`unsupported`
instruction to `ok` **only** when the target→field mapping is valid — the
magnitude is never changed implicitly. Quick "accept adjusted value" and preset
value buttons remain.

---

## 7. Confirm / Reject / Undo

- **Confirm** applies only `isApplicable` instructions to `history`, announces
  spoken confirmation when enabled, resolves the proposal to `confirmed`, and is
  guarded against a double submit by an applied-id set.
- **Reject all** resolves to `rejected`; nothing is applied.
- **Undo** removes a single applied command and logs an `undo` event; the model is
  always recomputed from the remaining history (no drift).

---

## 8. Event Timeline

`SessionTimeline` lists `SessionEvent`s newest-first with an icon, label, detail
and time. Event types cover the full lifecycle (`session_started/ended`,
`proposal_created/confirmed/rejected/cancelled`, `manual_edit`, `undo`, `reset`,
`scenario_saved/renamed/deleted/loaded`). Consecutive `manual_edit` events for the
**same** parameter are coalesced in `appendEvent`, so dragging a slider produces a
single running entry.

The panel states plainly that this is a process log, **not** a clinical audit
trail.

---

## 9. Scenarios, Load & Compare

`ScenarioPanel` supports save (current state), rename, delete (guarded by a
confirmation dialog), load, and marking a **final selected scenario** (used in the
export). A scenario stores a full canonical `ModelState`, so it is reproducible;
loading rebuilds the applied history via `stateToCommands()`.

`SimulationWorkspace` generalises the previous fixed *Original vs Simulated*
compare into **arbitrary A/B**: in Compare mode, two selectors choose from
`Original (baseline)`, `Current working`, and every saved scenario, feeding two
`FaceViewer` panes, plus a **parameter differences** table (value A, value B, Δ).
One rendering system is retained — the geometry engine is untouched.

---

## 10. Summary Export

`buildConsultationReport()` produces a Markdown summary **from actual session
data** and downloads it. It contains: session id/start/end/status, a
"storage: temporary" notice, the final working parameters, the original
instructions (transcript) with outcomes, the confirmed changes, **every proposal
that was not confirmed** (listed only as unresolved — never as applied), saved
scenarios, the final selected scenario, validation warnings, and an explicit
limitations section (not an EMR, not a clinical audit trail, illustrative scale).

The report button is disabled while there is no history.

---

## 11. Async-Safety & Data Integrity

- `parseText` captures the session id and a request token; the result is dropped
  if the session changed, the token is stale, or the session ended.
- A new utterance supersedes a still-actionable proposal by `cancelling` it.
- The applied-id set prevents a double-click from applying a change set twice.
- The model is always `applyAllCommands(history)` — reset/undo/load never leave a
  stale value behind.

- Scenario save ("Plan A") → summary "Bridge width +9mm · Tip height +3mm",
  selected.
- Compare: baseline vs current → diff rows `Bridge width 0→+9 mm`,
  `Tip height 0→+3 mm`; switching B to the scenario works.
- Report export: heading, "Storage: temporary", unresolved section, limitations,
  `Final selected scenario: Plan A` all present.
- End consultation → badge "Ended · temporary", End/Reset disabled, inputs
  disabled, pending proposal cancelled.
- New consultation with unsaved work → dialog "Start a new consultation?" →
  confirm → history empty, transcript empty, scenarios cleared, timeline reset to
  a single `session_started`.
- **Stale-response guard:** starting a new consultation while a parse was in
  flight left no stray transcript entry after the reply arrived.
- **No application console/log errors and no failed requests.**

## 14. Honest Limitations

- The whole consultation is **in-memory only**; it is lost on reload and is not a
  server record.
- The timeline is a process log, **not** a compliant clinical audit trail.
- Units/scale are illustrative (Phase 4/5) — no clinical validity.
- Compare is a side-by-side visual + numeric diff of the prototype parameters; it
  makes no claim about real tissue behaviour or outcomes.
